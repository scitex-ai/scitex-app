# Internationalisation

## The commands

```bash
scitex-app translations extract figrecipe._django -l ja   # makemessages: django (html, txt, py) + djangojs (js, ts, tsx)
scitex-app translations compile figrecipe._django         # babel, no msgfmt
scitex-app translations validate figrecipe._django        # exit 1 on untranslated, uncompiled or misplaced catalogs
```

`extract` needs GNU gettext (`xgettext`, `msgmerge`); the hub dev container has it.

## Wiring a leaf app

Standalone settings:

```python
from scitex_app.i18n import i18n_settings, with_locale_middleware
MIDDLEWARE = with_locale_middleware(MIDDLEWARE)
globals().update(i18n_settings())   # English default, Japanese available
```

Templates use `{% translate %}` as usual. TS/JS strings use scitex-ui's Django-compatible module:

```ts
import { gettext, ngettext, interpolate } from "@scitex/ui/src/scitex_ui/static/scitex_ui/ts/_base/gettext.ts";
<button title={gettext("Undo")}>{interpolate(ngettext("%s figure", "%s figures", n), [n])}</button>
```

and the page embeds the app's catalog once, before the bundle:

```django
{% load scitex_i18n %}
{% scitex_js_catalog "figrecipe._django" %}
```

Pass msgids as literals (xgettext extracts only literals); use `gettext_noop` in label tables and `gettext(label)` where rendered.
In tests, `scitex_ui.testing.assert_no_untranslated(html, english_strings)` checks a Japanese render.

## Where your catalogs go

```
<your_app>/locale/<lang>/LC_MESSAGES/django.po      source, committed
<your_app>/locale/<lang>/LC_MESSAGES/django.mo      compiled, SHIPPED IN THE WHEEL
<your_app>/locale/<lang>/LC_MESSAGES/djangojs.po    TS/JS strings
<your_app>/locale/<lang>/LC_MESSAGES/djangojs.mo    compiled, SHIPPED IN THE WHEEL
```

`<your_app>` is the Django app package (`figrecipe/_django`), not the distribution root: a
`figrecipe/locale/` is never loaded for `figrecipe._django`. `ScitexAppConfig` warns
(`scitex_app.W001`) when it finds one.

That is all. Django auto-discovers `locale/` for anything in `INSTALLED_APPS`,
so you need **no** `LOCALE_PATHS` entry, no registry, and no cooperation from
whatever is hosting you. Measured 2026-08-23: a probe app with only a `.mo` and
no host configuration translated correctly.

Strings owned by the **host** rather than by any app (a project's own base
templates, 404/500) use `LOCALE_PATHS` instead. The two mechanisms compose —
that is Django's design, not a workaround.

Shared vocabulary that appears in every app's chrome belongs in **`scitex_ui`**'s
catalog, since `scitex_ui` is already in `INSTALLED_APPS` everywhere. Translate
the shell once there and it is translated in every mounted app, standalone
included.

## Do not share one catalog across apps

Per-app catalogs, duplicates accepted. The same English string can need
different translations in different contexts, and deduplicating by `msgid`
silently asserts they are the same string — a translation error invisible in the
diff. Django's resolution order is deterministic, so duplicates cost effort, not
correctness.

## THE FAILURE THIS PAGE EXISTS TO PREVENT

A language with no compiled catalog does not error. gettext falls back to the
**source string**, so the page renders in English and looks like *"nobody has
translated it yet"* rather than *"the mechanism is broken"*. Measured twice, in
mirror-image forms:

| | activation | catalog |
| --- | --- | --- |
| scitex-hub | wired | **empty** |
| standalone (before 0.9.x) | **absent** | works |

Opposite causes, identical symptom. Neither showed up as a failure anywhere.

## Two things must BOTH be true

**1. A catalog must exist, compiled.** `.po` is source; only `.mo` is loaded. A
distribution carrying `.po` without `.mo` reproduces the silent fallback at every
consumer at once, each debugging it separately.

**2. Something must activate a language.** Standalone does this for you from
0.9.x — `LocaleMiddleware` is installed, so `Accept-Language` is honoured. Set
`SCITEX_LANGUAGES` to declare what you support and `SCITEX_LANGUAGE_CODE` for the
default. If you declare a language with no compiled catalog, startup says so
rather than degrading quietly.

## Compiling: `msgfmt` is NOT available

`django-admin compilemessages` shells out to the gettext `msgfmt` binary, which
is **absent from this container, from scitex-hub's container, and from
`scitex-hub-prod-django:latest` — the image serving production.** Three
environments, three absences. So `compilemessages` is not a portable answer here.

Compile with a pure-Python path instead (`babel.messages.mofile.write_mo`), **at
build time**, and include the `.mo` as package data so it is inside the wheel.
Not at install — wheels have no build step. Not at runtime.

## Gate it, or it will ship green

Add an assertion to your release pipeline that the compiled catalog is present
in the **built artifact**, not merely in the tree. "Present in the repo" and
"present in the thing running" are different claims and only the second one
matters. scitex-app does exactly this for its skills docs; copy that shape.

Without such a gate, *"we added Japanese"* and *"Japanese renders"* remain two
different claims, and the first one is the only one anybody checks.
